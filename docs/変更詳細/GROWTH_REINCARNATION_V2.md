## 新旧処理と適用範囲

- 基本能力は従来の3抽選から5抽選へ変更。職業+種族ウェイトと重複抽選を維持。HP1抽選は最大/現在とも+8、MPは最大のみ+3、6基本能力は+1。
- 属性は従来の6属性から毎レベル3抽選、各+1。属性ウェイト・重複抽選も変更なし。
- `apply_character_exp` の回復仕様は変更しない。探索・ボス戦は `apply_exploration_exp` 経由で全回復。闘技場では通常の現在HP/MPを呼出前の値へ戻し、レベルアップ後の闘技場HP/MP処理は既存サービスに従う。
- 既存キャラクターも次のレベルアップから新抽選数。過去レベルの再計算/追加付与なし。
- EXP量、必要EXP100、Lv100上限、戦闘/AGI/装備/スキル/勝敗/ボス値は変更なし。
- `level_up_once` は増加前のレベルを抽選番号として使う。Lv50→51はn=50。範囲外の番号は変更前に拒否し、共通EXP処理では既存の上限100判定を維持する。

## 初期配分と追加成長

新育成の累積配分を `125 * min(r,150) + 100 * max(r-150,0)` とする。
回帰の14項目均等抽選・全体の再抽選を維持し、HP換算+5、MP換算+2、他項目+1も維持する。
150回帰までを100倍へ置換することはない。

追加成長は `A=25*max(r-150,0)`、n回目は `5 + A*n//99 - A*(n-1)//99`。
基本能力の既存ウェイトを使い、属性抽選を増やさない。99回の合計は `495+A`。
すべての接頭区間で追加分が `A*n//99` と一致し、各レベルの回数差が最大1であることを検証した。

## 既存キャラクターの保護と認可

移行時の記録済み回帰回数をr0とし、`legacy_reincarnation_points=25*max(r0-150,0)` を保存する。
移行時はこの新列以外のキャラクターフィールドやM2Mを一切更新しない。
新規作成は保護分0。抽選履歴や能力値からの逆算は行わない。

今後の次回回帰では `calculate_initial_points(r+1)+legacy_reincarnation_points` を再配分する。
保護分は回帰後も保存し続ける。旧160回帰20,000ポイントの場合は保護分250、
次の161回帰は19,850+250=20,100、162回帰は19,950+250=20,200。
150以下の既存キャラクターは125増分で150まで進み、151回帰から100増分になる。

保護するのは再配分ポイントの資産総数である。回帰時の14項目再抽選は従来どおりなので、
個々の能力値は回帰で変動する。Lv1/EXP0リセット、放浪人への復帰、直前職業の永久スキル習得、
通常/闘技場HP・MP回復を維持する。

回帰の `transaction.atomic` / Character行ロック、ログイン・CSRF、所有権、二重確定防止は維持。
プレビューの世代に `growth-v2` と保護分を含め、移行前の125倍プレビューをそのまま確定できなくした。
旧プレビューでPOSTした場合は回帰せず、新しいプレビューを表示する。再確認後のPOSTで確定できる。
管理者が回帰回数だけを直接編集する既存デバッグ操作では、保護分は再計算しない。
保護分は移行時点の記録であり、通常回帰では変更しない。

## ボスバランスへの影響と未測定範囲

ボスの正式値・属性・技能、プレイヤー戦闘式は変更していない。勝率の新測定は未実施。
旧5-C等の保存済み能力profileをそのまま使う戦闘比較は、その固定能力に対する証拠として保持される。
同じ回帰数/Lvから再生成する新キャラクターは能力値が変わるため、旧勝率を新育成へ直接適用できない。

以下は能力実測からの推論であり、勝率の検証結果ではない:

- 低回帰のLv成長とHPが増え、序盤ボスの生存/攻略条件が緩和する可能性がある。
- 高回帰の低Lvは初期配分が少なく、育成途中は職業/種族によって旧式より低い戦闘力にもなる。
- Lv100では基本能力・HPが大幅に増えても、属性低下や職業別の能力差がある。旧B/C目標への適合、全職業の勝率上昇は断定できない。
- 既存高回帰の保護分を含むキャラクターと、保護分0の新育成は評価条件を分ける必要がある。

今後のバランス測定は今回の新成長条件、永久技能、装備、育成seed、戦闘seed、保護分を明示して行う。
本件の実装に未解決事項はない。新育成でのボス勝率・育成時間は未測定である。

## migration適用と復元

新migrationは `accounts.0023_character_legacy_reincarnation_points` の1件。
テストDBで適用・データ保護を検証済み。通常DBは未適用なので、通常画面を新コードで利用する前に別途適用が必要。
既存保護分は一度だけ旧方式時点の回帰回数から確定するため、旧コードでの回帰と移行作業を同時に走らせない。
別途承認後に、旧DBとコードをバックアップしアプリを停止した状態で計画を確認して適用する。

```bash
venv/bin/python manage.py migrate --plan
venv/bin/python manage.py migrate accounts 0023_character_legacy_reincarnation_points
```

上記は手順の提示のみであり、今回通常DBに実行していない。
`migrate --plan` で他の未適用依存migrationが出る場合は、実行対象を確認してから進める。

今回の作業時点では通常DB未適用のため、コードを開始HEADの対象ファイルへ個別に戻せばDBの逆移行は不要。
既存未追跡ファイルや他の作業を巻き込む一括復元・削除をしない。
適用後に0022へ逆移行すると保護列が失われ、再適用時にその時点の回帰数から計算されるため、
運用後の単純な逆移行/再適用を安全な復元として扱わない。
適用後の復元は保護情報とその後の育成を含めて別途設計する。migrationを戻しても新式で得た能力値は自動で旧値へ戻らない。

開始時の既存ファイル指紋・変更対象原本の控えは `/tmp/qhymia-growth-v2-before/` に保存した。
一時領域なので永続バックアップとはみなさない。旧ボス測定成果物や通常DBのバックアップを上書きしていない。
最終確認で、開始時592ファイル中の対象8ファイル以外の584ファイルはSHA256一致、既存ファイルの削除0。
対象8ファイルには元から未追跡だったAGENTS/コンテキストの更新を含む。
