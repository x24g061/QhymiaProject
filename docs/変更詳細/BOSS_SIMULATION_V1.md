# ボス対プレイヤー：初回測定と再実行・復元手順

実施日：2026-11-13（JST）。対象：1・6・7・12階、重戦士・ウィザード。

## 結果の位置づけ

120戦は実戦エンジンの動作確認と、測定用仮ビルドの比較。難易度の合否判定ではない。
通常DBを変更せず、Djangoのテスト専用DBで実施。戦闘中のSELECT以外のSQLを検出するガードを有効にした。
同一seed・同一条件で行動ログまで一致し、呼出前後の乱数状態も維持されることを確認した。

## プレイヤー条件

ヒューマン、全回復、ST100、装備なし、6属性値すべて0（無属性）。
測定ではレベル1・回帰0のレコードへ下表の能力値を直接設定する。育成で到達できるかは検証していない。
1階の条件も「0回帰Lv20の実成長結果」を意味しない。
6/7/12階の基準戦闘力は資料の目安に合わせたが、能力配分は測定用の仮条件。
実際の職業補正・種族補正・バフ・疲労は本体の計算で適用される。

## 観測した点と次の比較案

- 1階：基準・強条件は両職業5/5勝利。弱条件では重戦士3/5、ウィザード1/5。MP不足による通常攻撃への切替も発生した。
- 6階：基準は両職業0/5。強条件は重戦士4/5、ウィザード0/5。同じ合計戦闘力・同じ能力配分でも職業とスキル構成で結果が異なる。
- 7階：全条件0/5。ステラの連続攻撃に耐えられるHP・INT、先に動くためのAGI、攻撃構成を個別に比較する候補。全職業・実育成ビルドを見ずにボスを弱体化しない。
- 12階：基準は両職業0/5、強条件で両職業2/5。試行数を増やす前に、実際の装備や能力配分を含む条件を定める。
- 今回は全120戦で双方ともST0に到達しなかった。ST0・長期戦・MP枯渇後の挙動は既存ボス単体テストの確認と区別し、追加の長期戦条件を検討する。
- 本測定は戦闘エンジンのみ。ブラウザ、報酬付与、探索回数・階層解放は今回未確認。

能力値・倍率・仕様の調整は行っていない。次は7職業・実育成/装備条件への拡張を検討する。

## 生データ

`BOSS_SIMULATION_RUNS_V1.json` に全24条件の能力値、全120戦のseed・勝敗・ループ数、双方の終了HP/MP/ST、スキル別使用回数、発動失敗・MP不足回数、行動列とタイムラインを保存した。
成功スキル回数は残使用回数の差分から集計し、発動失敗・MP不足は行動ログから集計する。
ループ数は1対1のゲージ加算を測定するため、測定器は複数敵の集計には使用しない。

## 再実行

プロジェクトルートで実行。通常DBへのmigrateや、キャラクターの作成コマンドは不要。

```bash
# 通常の回帰テスト（各条件1戦＋再現性チェック）
venv/bin/python manage.py test apps.battle.test_boss_simulation --noinput

# 今回の120戦を再現（出力JSONを再生成する）
QHYMIA_SIM_TRIALS=5 \
QHYMIA_SIM_REPORT="$PWD/docs/変更詳細/BOSS_SIMULATION_RUNS_V1.json" \
venv/bin/python manage.py test apps.battle.test_boss_simulation --noinput
```

試行数は1〜1000で変更可能。出力先は別ファイルも指定できる。
既存レポートを残す場合は別名で出力する。実行にはPostgreSQLのテストDB作成権限が必要。
条件は `apps/battle/test_boss_simulation.py` の `BASELINES` / `PRESETS` で定義する。

## 変更範囲と復元

- 新規：`apps/battle/boss_simulation.py`（実エンジンの測定器）。
- 新規：`apps/battle/test_boss_simulation.py`（テストDBの仮ビルド・測定・再現性検証）。
- 新規：本資料とJSON生データ。
- 追記：`AGENTS.md`、`QHYMIA_CONTEXT.md`（測定の範囲・制約）。
- 本体の戦闘処理、能力値、通常DB、マイグレーションは今回変更していない。

測定追加だけを戻す場合は、新規Pythonファイル2つを `apps/` 外へ退避し、資料の今回の追記だけを取り消す。
資料の追記前バックアップは `.local-backups/boss-simulation-docs-before.zip`。
後から別作業が入っている場合はZIPで一括上書きせず、今回の追記分を比較して戻す。
ボス再設計本体を戻す必要はなく、DBの逆マイグレーションも不要。
